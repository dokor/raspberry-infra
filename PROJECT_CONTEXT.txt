Je travaille sur un homelab basé sur un Raspberry Pi 5.

Contexte technique :
- OS : Debian / Raspberry Pi OS 64 bits
- Docker + Docker Compose
- Traefik v3.x comme reverse proxy public principal
- réseau Docker externe `proxy` pour les services exposés
- réseau Docker externe privé `automation` pour n8n et les workers internes
- GitHub Actions avec runner self-hosted sur le Raspberry
- GHCR utilisé pour les images partagées du homelab
- aucun secret ou fichier .env de production versionné
- UFW + Fail2ban
- Grafana / Prometheus déjà présents

Architecture automation :
- une seule instance n8n centrale sur le Raspberry
- n8n possède l'orchestration : schedules, retries, conditions, validations et notifications
- `codex-bridge` expose Codex à n8n uniquement sur le réseau `automation`
- `codex-runtime` est une image Docker versionnée commune réutilisée par plusieurs services
- `browser-automations` porte Playwright / Chromium et les sessions navigateur
- les workflows n8n restent versionnés dans les repositories métier qui les utilisent
- les détails propres à un site ou une automatisation ne doivent pas remonter dans `raspberry-infra`

Organisation indicative :
/srv/
  ├─ infra/
  │   └─ raspberry-infra/
  │       └─ env/
  │           └─ n8n.env
  ├─ apps/
  │   └─ projets Docker
  └─ backups/

Déploiement :
- les applications métier peuvent être déployées depuis leur clone de production ou via checkout GitHub Actions selon le workflow
- les services d'infrastructure ont leurs workflows dédiés
- les migrations sensibles peuvent rester en `workflow_dispatch`
- les images partagées sont publiées sur GHCR
- les secrets de runtime persistent hors des workspaces temporaires du runner

Contraintes :
- Raspberry Pi 5 ARM64
- priorité à la simplicité, robustesse et lisibilité
- pas de Kubernetes
- pas de plateforme cloud d'hébergement nécessaire
- préférer des composants légers, reproductibles et documentés

Principes :
- éviter les services dupliqués entre projets
- centraliser les briques réellement transverses
- isoler les credentials, volumes et workspaces quand nécessaire
- ne pas exposer directement un service interne sans besoin explicite
- épingler les runtimes de production plutôt que dépendre implicitement de `:latest`
